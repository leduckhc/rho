# D-one-tls-stack — one provider, one TLS, or CI breaks

Date: 20260901. Reference: `D-one-tls-stack`.
Spec: `docs/specs/20260901-192551-SPEC-anthropic-messages-provider.md`.

## The question

`rho-provider-anthropic` needs `reqwest` for HTTPS. Which TLS backend does it use?

## The decision

**`rustls`, with the same features `rho-provider-openrouter` uses.**

```toml
reqwest = { version = "0.13.4", default-features = false, features = ["rustls", "json", "stream", "http2", "charset", "system-proxy"] }
```

## The reason

This repo enforces exactly one `rustls` version in `Cargo.lock`. The CI gate runs
`python3 bench/check-rustls.py` and fails when it finds two.

That guard exists because defect six in `.rho-work/progress.md` was a panicking
`rustls-webpki` pulled in by a feature name that looked safer than the modern one.
Dependabot found it on the first push.

Every provider crate uses `reqwest`. They must all use the same TLS backend, or the lock
holds two versions and CI fails.

The name changed: `native-tls` became `rustls-tls` and then `rustls`. Following the
features another crate already uses keeps one stack.

## What it rules out

**Hand-writing the feature list.** `rho-provider-openrouter` is already working. Copy its
features verbatim.

**Using `native-tls` or `rustls-tls`.** Those are old names. The modern feature is
`rustls`.

**Adding a second TLS backend.** One backend per repo. The CI guard enforces it.

## The cost

None. The feature line is one copy-paste from an existing `Cargo.toml`.
