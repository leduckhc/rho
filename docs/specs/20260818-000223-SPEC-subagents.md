# SPEC-subagents — Subagents

Status: delivered in sprint 2.
Owning crates: `rho-core` for the spawner and the policy composition, `rho-tools` for the
tool, `rho-skills` for reading an agent definition.
Features: a new row, F-subagent-spawning to F-agent-definitions. See `docs/features.md`.

Every contract named here is collected in `docs/contracts-subagents.md`. That page is the
reference. This page is the reasoning.

## 1. Why rho does this differently

A subagent exists to keep work out of the parent's context. The parent asks for a result,
a child does the reading and the trying, and only a summary comes back.

jcode pays an OS process per child. pi uses an in-process session, confirmed by reading its source.

| Harness | A child is | Published cost |
| --- | --- | --- |
| jcode | an operating-system process, coordinated by a server | about 10.4 MB per session |
| pi | an in-process session, created inside the same Node process | no extra process, so no published per-child figure |
| rho | another `Session` on the same runtime | about **247 KB** per live session |

**Read the pi row carefully, because it limits what rho may claim.** `docs/benchmarks.md`
publishes about 76.5 MiB for pi, and that figure is per session **process**. A pi child adds
no process, so the figure does not apply to a child. rho therefore claims no advantage over
pi on a single child. See decision D-pi-subagents-are-in-process.

The rho figure is measured, in `docs/benchmarks.md`: 100 concurrent live sessions in
34 MiB. So the interesting number is not the saving on one child. It is that a fan-out of
fifty is ordinary rather than heroic.

**That is the only structural advantage claimed in this spec.** Everything else here is
either taken from prior art with credit, or an improvement that any harness could copy.

## 2. What we take, and from whom

**From pi.** An agent is a **file**, not a hard-coded role. A markdown file with
frontmatter names the agent, describes when to use it, and may narrow its tools and choose
its model. rho already parses exactly this shape in `rho-skills`, so the loader is reused
rather than rewritten. pi also streams a child's progress and tracks usage per child, and
both are kept.

**From jcode.** Three robustness ideas that a first attempt would miss.

- A **dead-worker salvage** path. When a child dies holding work, the work returns to the
  queue instead of vanishing.
- A **reclaim cap** on that salvage. jcode's `MAX_DEAD_ASSIGNEE_RECLAIMS` marks a task
  failed after N deaths, rather than requeueing a poisoned task forever. This is the detail
  that turns salvage from a loop into a guarantee.
- **Two separate limits**: a live-worker budget and an absolute cap. One protects the
  machine, the other protects a run from fanning out.

**From jcode, adapted.** jcode reconstructs the spawn tree by walking a
`report_back_to_session_id` chain, with a visited set to guard a cycle. rho stores the
parent link directly, because it is in one process and can, and it keeps the cycle guard,
because a bug is still possible.

## 3. The security core, and why the first design was wrong

The obvious rule is "a child may be no more permissive than its parent". The first draft of
this work said exactly that, and it is **not implementable as written**.

`ApprovalPolicy` is a trait object:

```rust
async fn approve(&self, tool: &str, kind: ToolKind, args: &Value) -> ApprovalDecision;
```

It has no ordering and no comparison. Two arbitrary policies cannot be ranked, so
"at most as permissive" cannot be computed. A design that claims to check it would be
lying.

**So the rule is expressed as composition, not comparison.**

```rust
/// Allow a call only when **both** policies allow it.
///
/// This is how a child is confined. The parent's policy is always one of the two
/// conjuncts, so a child can only ever be more restrictive. Escalation is not
/// checked, it is unrepresentable.
pub struct BothPolicies {
    parent: Arc<dyn ApprovalPolicy>,
    child: Arc<dyn ApprovalPolicy>,
}

#[async_trait]
impl ApprovalPolicy for BothPolicies {
    async fn approve(&self, tool: &str, kind: ToolKind, args: &Value) -> ApprovalDecision {
        match self.parent.approve(tool, kind, args).await {
            ApprovalDecision::Deny => ApprovalDecision::Deny,
            ApprovalDecision::Allow => self.child.approve(tool, kind, args).await,
        }
    }
}
```

Two consequences follow, and both are the point.

- A child of a `ReadOnlyPolicy` parent cannot write, whatever its own definition asks for.
- A child that names no restriction inherits the parent's policy unchanged.

**The tool set follows the same rule.** pi's agent frontmatter lists tools, and that list
is independent of the caller, so a child could receive a tool its parent never had. rho
**intersects** instead: the child's tool set is the parent's set filtered by the child's
list. A name the parent does not hold is dropped, and the drop is reported to the caller so
a mistake in a definition is visible rather than silent.

**This is an improvement over both, and it is cheap.** It costs one wrapper type and one
set intersection, and it removes a whole class of privilege escalation by delegation.

## 4. What a child inherits

| Thing | Inherited | Why |
| --- | --- | --- |
| Provider | yes | A child talking to a different service would surprise the payer. |
| Model | yes, overridable by the definition | A cheap model for a scout is the main reason to override. |
| Session root | yes, never overridable | The root is a security boundary. A child that could move it would escape confinement. |
| Sandbox mode | yes, never weakened | A child may ask for a stricter mode. It may not ask for a weaker one. |
| Approval policy | yes, composed with `BothPolicies` | See section 3. |
| Tool set | the parent's, intersected with the child's list | See section 3. |
| Context | **no** | A fresh conversation is the entire point. |
| Task registry | **no** | A child's background task must die with the child. |
| Budget | shared, tree-scoped | See `SPEC-budget-governor`. |

## 5. Definitions on disk

The same shape as a skill, so the loader is shared.

```markdown
---
name: scout
description: Fast recon. Locates code and returns a compressed summary. Use before planning.
tools: read, glob, grep
model: anthropic/claude-haiku-4.5
max_turns: 12
---

You locate code and report where things are. You do not change files.
Answer in under 200 words, with file paths and line numbers.
```

Discovery follows `SPEC-skills` exactly, including its trust rule, and that rule matters more
here than it does for a skill.

**A project agent is withheld until the user trusts the root.** A skill from the repository
is instructions. **An agent definition from the repository is instructions plus a tool
list plus a model choice**, and it runs unattended. So the same decision, D-project-skill-needs-trust, applies
with more force, not less.

Frontmatter rules:

| Field | Required | Rule |
| --- | --- | --- |
| `name` | yes | The same character rules as a skill. |
| `description` | yes | The model reads this to choose. `spawn_agent` puts every name and its description into the tool description, and the names into a schema `enum`. Without it, the agent cannot be chosen, so it does not load. |
| `tools` | no | Intersected with the parent's set. An unknown name is dropped and reported. The keywords `all` and `*` inherit the whole parent set, and `none` gives no tools. A keyword must stand alone. See decision D-a-tool-keyword-stands-alone. |
| `model` | no | Overrides the inherited model. |
| `max_turns` | no | Capped by the parent's remaining budget. |
| `sandbox` | no | May only narrow. `strict` from a `confined` parent is fine. The reverse is refused. |

## 6. The result contract

**The parent's context receives a summary and nothing else.** If a child's transcript
reached the parent, the feature would cost context instead of saving it, which is the one
mistake that makes a subagent pointless.

```rust
/// What a child returns to its parent.
#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
pub struct AgentReport {
    pub agent: String,
    pub outcome: AgentOutcome,
    /// The child's final answer, capped. This is what the model sees.
    pub summary: String,
    /// Every turn's usage, summed. Feeds the budget governor and the status line.
    pub usage: Usage,
    pub turns: u32,
    /// Where the full transcript was written, for a human. Never sent to the model.
    pub transcript: Option<PathBuf>,
}

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum AgentOutcome {
    Done,
    /// The child hit its own turn cap. The summary holds what it had.
    OutOfTurns,
    /// The child was cancelled, with its parent or alone.
    Canceled,
    /// The child failed. The parent continues.
    Failed { reason: String },
}
```

The task definition, the definition of done, and the verified artifact for `AgentReport` are specified in `SPEC-agent-tasks`.

**A child failure is a result, not the end of the run.** This is decision D-measured-cost-and-cache's rule,
restated where it is easy to forget: a tool error returns to the model so it can choose
again. A dead child must not kill its parent.

**rho keeps the full transcript on disk.** A child's events are already in this address space. Writing them to the session directory costs a file write. The file is readable without going through the session object. The writer creates the directory first. It did not before, so every real run lost its transcript to a warning. See `docs/verification/subagents-bedrock.md`.

## 7. Limits, and there are four

A child that spawns a child fans out geometrically. One limit is not enough.

```rust
#[derive(Clone, Copy, Debug)]
pub struct SubagentLimits {
    /// How deep the tree may go. A depth of 0 forbids spawning.
    pub max_depth: u32,
    /// How many children one parent may run at once.
    pub max_children_per_parent: usize,
    /// How many agents may be live in the whole process, at any depth.
    /// jcode's absolute cap, and it protects the machine rather than the run.
    pub max_live_total: usize,
    /// How long a child may run before it is cancelled.
    pub child_timeout: Duration,
    /// How many tool calls one child may make.
    ///
    /// A turn cap counts provider round trips. It does not bound a turn that
    /// asks for forty tool calls inside one request. This field counts every
    /// call across the whole run. See section 7.
    pub max_tool_calls: u32,
}
```

Defaults are stated in the constructor, not hidden, per decision D-no-four-argument-session-new. The starting
values: depth 2, four children per parent, 32 live in total, a ten-minute child
timeout, and 64 tool calls.

**Only a flag changes a limit today.** `rho-config` parses a `[subagents]` layer and merges it,
and no binary reads the resolved config yet. So a config file cannot change a subagent limit.
That gap covers the whole config crate, and it is recorded in decision
D-the-layered-config-has-no-caller. Do not claim the config keys work until that call site exists.

**A turn cap does not bound a turn that asks for forty tools.** A turn cap counts
provider round trips. One turn can request forty tool calls. All forty run before
the turn count increments. `max_tool_calls` counts every call across the whole run.
It stops work that a turn cap misses. `AgentStopReason::MaxToolCalls` maps to
`AgentOutcome::OutOfTurns`, so the parent gets what the child had. The CLI flag is
`--max-agent-tool-calls`.

**`rho-cli` makes the depth cap unreachable, on purpose.** The CLI captures the parent tool
set before `spawn_agent` joins it, so no child receives `spawn_agent`. A grandchild is then
impossible, whatever `max_depth` says. The cap stays, because a library caller may pass
`spawn_agent` to a child and then needs it. A live sweep confirmed the CLI behaviour. See
`docs/verification/subagents-bedrock.md`.

**A fan-out is one tool call.** `spawn_agents` takes a list of tasks and runs them together.
`AgentLoop::dispatch` stays sequential, because concurrency there would apply to `edit`,
`write`, and `bash`, and would race two approval prompts. A refused task is a per-task
result, and results report in request order so the prompt prefix stays stable. See decision
D-fan-out-is-one-tool-call.

**With a fan-out, the per-parent cap and the process-wide cap trigger.** Before it, only the
timeout could.

**Only the timeout triggers without a fan-out.** `AgentLoop::dispatch` runs tool calls
one at a time, so a session never holds two live children, and a slot frees between two
sequential spawns. The per-parent cap and the process-wide cap are for a host that runs many
sessions in one process, and for a library caller that spawns children concurrently. A
measured table is in `docs/verification/subagents-bedrock.md`.

**A cycle guard, even though the tree cannot cycle.** The parent link is stored directly,
so a cycle needs a bug rather than a race. The walk still carries a visited set, because
the cost is one small set and the failure without it is an infinite loop inside a lock.

**Refusing must teach, and it must not name a flag that does not exist.** Every refusal names
the limit, its value, and what to do: `the depth limit is 1 and this would be depth 2. Do the
work here. A subagent started from the rho command line holds no spawn tool, so it cannot
delegate further.` The first draft named `--max-agent-depth`, and no such flag exists, so it
sent the reader after a fix that could not work.

## 7a. A live child is addressable, and a background child is pollable

A count cannot be cancelled, steered, or watched. So the registry holds a handle per live
child, and the handle is the contract a frontend and a tool both use.

```rust
pub struct LiveAgent {
    pub id: AgentId,
    pub agent: String,
    pub depth: u32,
    // The ancestor chain is private. It is what makes ownership checkable.
}
impl LiveAgent {
    pub fn cancel(&self);
    pub fn is_cancelled(&self) -> bool;
    pub fn cancel_token(&self) -> CancelToken;
    pub fn progress(&self) -> AgentProgress;
    pub fn steer(&self, message: Vec<ContentBlock>) -> Result<usize, QueueError>;
    pub fn queued(&self) -> usize;
}
```

**Every lookup is scoped to the caller's own descendants.** The registry is process-wide, so a
bare id resolved against it let one session cancel another session's child. `live_under`,
`descendant`, `cancel_descendant`, and `status` all take the calling node. The unscoped views
are private, because a doc comment is not a boundary: the `agent_status` tool reached for the
unscoped one first. See decision D-a-caller-addresses-only-its-own.

**A background spawn returns the id, not the work.** `spawn_agent` takes `background: bool`.
The default is false, and the call then blocks, so the parent can never poll it. With
`background: true` the tool waits on a `oneshot` for the id alone and returns at once. A limit
refused before the child began still returns an ordinary tool result.

**A finished child still answers, because that is when the parent asks.**

```rust
pub enum AgentStatus {
    Running { agent: String, depth: u32, progress: AgentProgress, queued: usize },
    Finished { report: AgentReport },
}
```

`ChildSlot::drop` removes the live handle the moment the child ends, and a background child
usually ends while its parent is busy. So the registry records the report and `status` answers
from it. The store keeps the last 64 reports, oldest dropped first, because a report holds a
summary the model wrote and an unbounded store of model output already cost this project
805 MB once. See decision D-bash-line-cap. `AgentReport` carries no id, so the id and the
ancestor chain are kept beside it. A match on ancestors alone would answer with another
child's report, which is worse than answering nothing.

**A fan-out cannot be backgrounded.** `spawn_agents` runs its tasks together and blocks until
all of them finish. A parent that wants to work beside its children calls `spawn_agent` with
`background: true`, once per child.

**`agent_status` is `ToolKind::Read`.** Reading a child's progress changes nothing, so a
read-only session may poll a child it could not have spawned. `steer_agent` and `cancel_agent`
stay `ToolKind::Execute`, because both change what a child does.

## 8. Salvage, from jcode, with its cap

When a child dies without reporting, the parent must learn. Silence is the failure mode
that wastes the most time.

- A child that ends without a report yields `AgentOutcome::Failed` with the reason, and the
  parent's tool result says so.
- A parent that is cancelled cancels every descendant, through a **derived** `CancelToken`.
  `CancelToken::child` follows its parent in one direction. `AgentEvents::drop` aborts the
  driver, which drops the provider stream and any running tool future.
- **A child must not cancel its parent.** The first build shared one token, so a child that
  passed its timeout cancelled the whole session and the run ended with no answer and exit
  zero. A derived token fixes the direction. See `docs/verification/subagents-bedrock.md`.
- **The tool states the outcome.** A cancelled or failed child leaves an empty summary, so
  the tool result names the outcome and what to do next. Returning only the summary gave the
  model an empty string.
- **A retry has a cap.** If a caller re-delegates the same work and the child dies again,
  the count is tracked, and after `MAX_CHILD_RETRIES` the work is reported failed rather
  than retried. This is jcode's reclaim cap, and without it a poisoned task loops until the
  budget is gone.

## 9. Events

The parent's stream shows the child, or a frontend cannot render one.

```rust
    AgentSpawned { id: AgentId, agent: String, depth: u32 },
    AgentProgressed { id: AgentId, turns: u32, usage: Usage },
    AgentFinished { id: AgentId, report: AgentReport },
```

**New variants rather than reusing `TaskStart` and its siblings.** A task is an
operating-system command with an exit code. An agent has turns, token usage, and a summary.
Sharing one variant would force a frontend to guess which it was holding. `SPEC-background-tasks` keeps
its variants, and this spec adds three.

**Implementation status.** The three variants exist in `rho-core` and are emitted.
`ToolContext` gained `agent_events: Sender<AgentEvent>`. It is wired in
`Driver::dispatch_one` alongside the existing `ToolUpdate` forwarding. A drain runs after
the tool returns. That drain carries `AgentFinished`, so the report never drops. Tests
are in `crates/rho-tools/tests/subagent_tool.rs`.

### A read-only session cannot delegate, and that is deliberate

`spawn_agent` declares `ToolKind::Execute`, so `--read-only` denies it. A live check
confirmed the refusal.

There is a real argument the other way. Section 3 guarantees a child is never more permissive
than its parent, so a read-only parent produces a read-only child, and delegating research to
a scout would be safe. Denying it makes `--read-only` stricter than it needs to be, and it
blocks the case a read-only session would most want.

**It stays denied, for one reason: a tool cannot vary its `ToolKind` per call.** `SPEC-background-tasks`
met the same wall and split `task` from `task_cancel` for exactly this reason. Under a
permissive parent, spawning genuinely is mutating, because the child can write. So a single
tool must declare the stricter kind, and decision D-todo-in-a-green-stage says an uncertain boundary fails
closed.

A later change could add a second, read-only spawn tool that refuses to grant any mutating
tool to its child. That is a new tool and a new decision, not a tweak, so it is out of scope
here and recorded rather than left as a surprise.

## 11. What this does not give you

**No fault isolation.** This is the honest cost of the whole design. Sessions share an
address space, so a panic in a child can take down the process, and a leak in a child costs
its siblings memory. jcode and pi buy isolation with a process each, and they pay about
forty times the memory for it. rho trades isolation for density.

Two mitigations, and neither is a fix. A tool call runs inside a task, so a panic there is
caught at the task boundary rather than unwinding the process. And a child's memory is
bounded by the same caps as any session.

**A host that needs true isolation should run rho in separate processes**, which works
because rho is a library. That choice belongs to the host, not to this spec.

Also absent:

- No cross-process swarm, and no coordination server. jcode has one; this is a library.
- No task graph or dependency plan between children. jcode's `VersionedPlan` is a real
  feature and it is a separate spec.
- No persistence. A child dies with its parent process.
- No cost prediction before spawning. The budget governor stops work after the fact, one
  turn late, until the model hooks land. See `SPEC-budget-governor`.

## 12. Out of scope for sprint 2

- A workflow preset that chains agents, as pi's prompt templates do. It needs the command
  layer, F-slash-commands.
- A frontend view of a running tree.
- A child spawning against a different provider.
