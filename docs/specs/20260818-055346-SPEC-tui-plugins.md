# SPEC-tui-plugins — Third-party views for the terminal interface

Status: draft for sprint 3, stage U2.
Owning crate: `rho-tui`. Consumed by `rho-cli`.

A third party extends the terminal interface with a compiled Rust trait. rho draws the
data the trait returns. The trait never touches the frame, never reads a clock, and never
does IO during a render. This keeps every rule in `SPEC-tui`: the state is a pure function
of events, the render is pure and testable with a test backend, and input never blocks on
model work.

This spec designs the surface, not the visual layout. The layout lives in
`docs/tui-design.md`, owned by a sibling stage.

Features covered: F-custom-tool-renderer, in part. This spec ships the transcript view and
defers the other slots. See section 3.

## 1. Which tier this is, and why

`docs/extending.md` names three tiers. This surface is **Tier 2, an extension**: a
compiled Rust trait a third party implements, exactly like `rho_core::Tool` and
`rho_core::Hook`. There is no registry to join and no manifest to write. See
D-tui-plugin-is-a-tier-2-trait.

It is not Tier 1, the subprocess plugin loader of `SPEC-hooks-and-plugins` and
`ADR-plugin-mechanism`. A render runs many times per turn, so a per-frame stdio round trip
would break the frame budget and would do IO on the draw path. The trait is in-tree and
in-process. This spec extends the two-tier plugin decision; it does not re-litigate it.

It is not a fourth tier. The three tiers stay as they are.

## 2. The public API, verbatim

This block compiles against `rho-core` and `rho-tui`. A scratch crate proved it. See
section 9.

```rust
use std::sync::Arc;

/// A theme role. A view styles by role, never by a raw colour, so a user theme and a
/// no-colour terminal keep working. The enum is closed and names no colour, so a view
/// cannot request a colour rho does not define. The code does not compile if it tries.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Role {
    /// Default transcript text.
    Text,
    /// A dimmed, secondary note.
    Dim,
    /// An emphasised token.
    Accent,
    /// A success marker.
    Success,
    /// A warning marker.
    Warning,
    /// A failure marker.
    Failure,
}

/// One styled run of text a view returns. The text is untrusted. rho sanitises it.
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct PluginSpan {
    pub role: Role,
    pub text: String,
}

/// One line a view contributes to the transcript. It is data, never a frame.
#[derive(Clone, Debug, PartialEq, Eq, Default)]
pub struct PluginLine {
    pub spans: Vec<PluginSpan>,
}

/// Who authored one transcript entry a view may read.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TranscriptRole {
    User,
    Assistant,
    Thinking,
}

/// A read-only projection of one transcript row a view may read. It holds only the
/// author and the visible text. A tool result, an approval prompt, and a
/// credential-shaped value are never projected here.
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct TranscriptEntry {
    pub role: TranscriptRole,
    pub text: String,
}

/// The owned, `Send` input passed to one render. It is data only. A view holds no
/// handle to the session, so a view cannot send input or approve a tool call.
#[derive(Clone, Debug, PartialEq, Eq, Default)]
pub struct RenderInput {
    /// A monotonic frame counter for motion. It is not wall-clock time. A view animates
    /// by `tick`, so its output stays a pure function of its inputs.
    pub tick: u64,
    /// The columns available to the transcript area.
    pub width: u16,
    /// The transcript projection, when the user granted `Grants::read_transcript`. It
    /// is empty otherwise. It never carries a tool result, an approval, or a credential.
    pub transcript: Vec<TranscriptEntry>,
}

/// What the user granted one view. rho sets it from the user config. A view cannot set
/// its own grant, so a peer does not classify itself.
#[derive(Clone, Copy, Debug, PartialEq, Eq, Default)]
pub struct Grants {
    /// Read the transcript. Off by default. The user opts in.
    pub read_transcript: bool,
}

impl Grants {
    /// No access. This is the default.
    pub fn none() -> Self {
        Self { read_transcript: false }
    }
    /// Read the transcript. The user opts in to this.
    pub fn read_transcript() -> Self {
        Self { read_transcript: true }
    }
}

/// A third-party view that contributes rows to the transcript. This is a Tier-2
/// extension: a compiled Rust trait object, like `rho_core::Tool` and `rho_core::Hook`.
pub trait TranscriptView: Send + Sync + 'static {
    /// A stable name, for logs and for the diagnostic row. rho sanitises it.
    fn name(&self) -> &str;

    /// Draw the rows this view contributes. Pure. No IO. No clock read. rho runs it on a
    /// worker thread, bounds it by the budget, and sanitises every span.
    fn render(&self, input: &RenderInput) -> Vec<PluginLine>;
}

/// The registry of TUI extensions. Registration order is draw order.
#[derive(Default)]
pub struct TuiExtensions {
    views: Vec<(Arc<dyn TranscriptView>, Grants)>,
}

impl TuiExtensions {
    pub fn new() -> Self {
        Self { views: Vec::new() }
    }
    /// Register a view with the grants the user gave it. The grants come from rho, not
    /// from the view.
    pub fn register_view(&mut self, view: Arc<dyn TranscriptView>, grants: Grants) -> &mut Self {
        self.views.push((view, grants));
        self
    }
    pub fn views(&self) -> &[(Arc<dyn TranscriptView>, Grants)] {
        &self.views
    }
}

/// The per-view render budget, in milliseconds. rho waits at most this long for a view.
pub const PLUGIN_RENDER_BUDGET_MS: u64 = 8;
```

The registration call is `TuiExtensions::register_view`. The type a view returns is
`Vec<PluginLine>`. The surface is small on purpose. A wide surface cannot stay stable.

## 3. What a view may draw, and where

A view returns `Vec<PluginLine>`. rho appends the lines to the transcript area that
`SPEC-tui` section 4 already defines, below the model rows and above the status line. rho
draws them in registration order. This is the one slot sprint 3 delivers.

| Slot | Sprint 3 | Note |
| --- | --- | --- |
| A row in the transcript | **delivered** | Through `TranscriptView`. |
| A custom rendering for a named tool | deferred | A later addition to `RenderInput`. See F-custom-tool-renderer. |
| A widget above the composer | deferred | Needs a second slot and a layout change the designer owns. |
| A status segment | deferred | Needs a bounded, fixed-width slot on the status line. |

A deferred slot is a new method or a new input field, added with a default body, so an
existing view keeps compiling. This mirrors the lifecycle-point rule in
`SPEC-hooks-and-plugins` section 3.

## 4. The purity rule

A view render is a pure function of its `RenderInput`, plus `input.tick` for motion. The
rules match `SPEC-tui` and the codex correction in `docs/tui-prior-art.md`.

- A view may not read a clock. rho passes `tick`, a monotonic frame counter, so a shimmer
  or a spinner stays a pure function of its input. This is the exact defect rho refuses in
  codex `shimmer.rs`, which reads a process-wide `Instant` inside the render.
- A view may not do IO during a render. The trait gives it no file handle, no socket, and
  no frame.
- A view returns data. rho draws it. A view never writes to the terminal.

**The budget.** rho waits at most `PLUGIN_RENDER_BUDGET_MS`, which is 8, for one view. rho
runs the render on a worker thread and reads the result with a deadline. See
D-tui-plugin-render-budget.

**On a timeout.** rho drops the view output for that frame. It draws one dim placeholder
row, `plugin <name> skipped`, with the name sanitised. rho then disables the view for the
rest of the session, so one slow view cannot slow every later frame. rho cannot force a
runaway worker thread to stop, so it stops feeding it and ignores its result. The next
frame draws `plugin <name> disabled`.

## 5. The trust boundary

A view is untrusted code, linked into the binary. The same principle as `SPEC-mcp`
section 6 applies: a peer does not classify itself. rho decides what a view may read and
do, from the user config. A view cannot widen its own access.

- **May a view read the transcript?** No, by default. `Grants::none` is the default, and
  `RenderInput::transcript` is then empty. The user opts in with `Grants::read_transcript`.
  See D-tui-plugin-trust-default-no-transcript.
- **May a view read a tool result, an approval prompt, or a credential-shaped value?** No.
  `TranscriptEntry` projects only a user, assistant, or thinking row, and only its visible
  text. A tool result, an approval prompt, and a credential never enter that projection. A
  credential never reaches a view under any grant. Redaction happens before the projection,
  by the `rho-redact` home that D-one-redaction-home defines.
- **May a view write to the terminal directly?** No. A view returns `Vec<PluginLine>`. rho
  owns the frame. A direct write would corrupt the frame, so the trait exposes no writer
  and no frame.
- **May a view send input, or approve a tool call?** No. `RenderInput` is data only, and it
  carries no handle to the session, no sender, and no approval channel. Approving is
  impossible, not discouraged, because the surface has no type through which to express it.
- **What happens when a view panics or crashes?** Read this answer in two halves, because
  the honest answer differs between a test build and a release build.
  - A view that returns bad data, returns nothing, or exceeds its budget is contained. rho
    draws the `plugin <name> disabled` placeholder and disables the view for the session.
    rho never calls `unwrap` on a view result.
  - A view that **panics** does not unwind in a release build. The workspace release
    profile sets `panic = "abort"` in `Cargo.toml` line 33, so a panic aborts the process
    before any thread can unwind. So rho does **not** claim that a panicking view leaves the
    session alive in release. It claims it only under a profile that unwinds, which the test
    profile does.
  - So a linked view is trusted not to panic, and that trust is the price of drawing inside
    the frame. A view whose author rho does not trust belongs out of process, which this
    sprint does not ship. `F-out-of-process-plugin-tier-2` already carries that guarantee
    for a tool, because a subprocess death is not a process death.
  - `panic = "abort"` is a measured footprint decision, and this spec does not reopen it.
    See `ADR-footprint` and `D-tui-plugin-render-budget`.

## 6. Sanitation

Any text a view returns is untrusted. Every `PluginSpan::text`, and the view `name`, pass
through `crate::sanitize_line` and then `fit_to_width`, in `crates/rho-tui/src/sanitize.rs`.
This is the same filter that MCP output and tool output pass through, from the one home
that D-one-redaction-home defines. So a control sequence cannot move the cursor, clear the
screen, or hide text.

A view cannot bypass the filter. The only path from a view to the screen is a returned
`PluginLine`, and rho sanitises every span on that path. A view has no frame and no writer,
so there is no second path.

## 7. The theme contract

A view styles by `Role`, never by a raw colour. The theme maps each role to a concrete
`Style`, and that map is the only place a colour is chosen. A no-colour terminal maps a
role to a modifier, so bold, dim, and reverse still separate the roles. A user theme
remaps the same role list. This follows the named-role finding from jcode in
`docs/tui-prior-art.md`: a role list is testable, and a colour list is taste.

The role list is the `Role` enum in section 2: `Text`, `Dim`, `Accent`, `Success`,
`Warning`, and `Failure`.

**A view that wants a colour rho does not name cannot express it.** The surface has no
colour type and no `Rgb` constructor. A view that tries to name a colour does not compile.
This is a compile-time refusal, not a runtime check. See F-themes for the theme itself.

## 8. Test cases

All render tests use `ratatui::backend::TestBackend`. No test opens a real terminal. The
tests live in `crates/rho-tui/tests/`.

- `view_contributes_a_row_to_the_transcript` — a registered view returns one line, and the
  frame buffer holds its text below the model rows.
- `views_draw_in_registration_order` — two views draw, and the first registered draws first.
- `a_view_over_budget_is_dropped_within_the_budget` — a view that sleeps past the budget is
  abandoned within `PLUGIN_RENDER_BUDGET_MS`, and the frame holds the placeholder, not the
  slow output. A fake clock in the harness bounds the wait; the view still reads no clock.
- `a_slow_view_is_disabled_after_one_timeout` — a view dropped once is not called again in
  the session, and later frames hold the `disabled` placeholder.
- `a_panicking_view_is_disabled_and_the_session_survives` — a view whose render panics
  yields the placeholder, the app keeps running, and no later frame calls the view.
- `a_view_without_the_grant_sees_an_empty_transcript` — a view with `Grants::none` receives
  an empty `RenderInput::transcript`, even when the transcript has rows.
- `a_granted_view_sees_only_visible_text` — a view with `Grants::read_transcript` receives
  user, assistant, and thinking text, and no tool result, approval, or credential.
- `render_input_exposes_no_session_handle` — the `RenderInput` type carries no sender and
  no approval channel, so a view cannot send input or approve a tool call. This is a
  type-level assertion, proven by a compile-fail fixture.
- `a_view_span_with_an_escape_sequence_is_sanitised` — a real escape sequence in a returned
  span never reaches the frame buffer, and the visible letters survive.
- `a_view_name_with_an_escape_sequence_is_sanitised` — the placeholder row sanitises the
  view name.
- `a_raw_colour_does_not_compile` — a fixture that names a colour on the surface fails to
  compile, proven with `trybuild`. The `Role` enum is closed and names no colour.

## 9. The scratch crate result

The section 2 block compiled as a library. The scratch crate was
`/tmp/rho-tui-plugins-check`, with a path dependency on `rho-core` and `rho-tui`, and a
dependency on `ratatui` for the role-to-style map. `cargo check` finished with no error.
The crate defined the proposed surface, a role-to-style map, a sanitation call through
`rho_tui::sanitize_line` and `rho_tui::fit_to_width`, and a sample third-party view.

## 10. Out of scope

- The visual layout, spacing, glyphs, and motion design. `docs/tui-design.md` owns them.
- The custom named-tool renderer, the composer widget, and the status segment. Section 3
  defers them.
- The theme itself, its colours, and its config. See F-themes.
- A keybinding a view registers. See F-keybindings.
- A view that mutates state, sends a prompt, or steers a turn. The surface is read and
  draw only, by design.
- A view delivered as a Tier-1 subprocess. Section 1 states why a per-frame subprocess
  does not fit the render path.
- A release-safe panic isolation under `panic = "abort"`. See D-tui-plugin-render-budget
  for the caveat and the deferral.
