# ADR-jsonl-codec — The JSONL codec for the session log

Status: accepted. Sprint 2.
Deciders: the owner, from measured numbers.

## Context

The session log is JSONL (`SPEC-sessions`). One record is one line. The file is
append-only. Two paths use the codec:

1. **Append.** One record encodes, then one line is written.
2. **Resume.** Every line decodes, in order, into the record enum.

A provider also parses JSON, and that path is hotter than either of the two
above. An SSE stream arrives as many small JSON objects, and the provider reads
them as untyped values.

The owner asked for the most efficient library for the job. So the candidates
were measured, not ranked from memory.

Candidates: `serde_json`, `sonic-rs`, and `simd-json`.

## The measurement

The bench crate is `bench/jsonl-codec`. It is standalone on purpose, because it
pulls two JSON crates that the workspace does not depend on.

```sh
cd bench/jsonl-codec
cargo run --release -- ~/.pi/agent/sessions/<project>/<file>.jsonl
```

Corpus A is a real 1848-record pi session file, 5.28 MiB of JSONL, with long text
fields. Corpus B is 50000 short records in the tool-event shape, 7.66 MiB.

Platform: macOS on Apple Silicon (aarch64), rustc 1.95.0, release build with
`lto = "fat"` and `codegen-units = 1`. Each number is the best of 30 rounds.

| Path | Corpus | `serde_json` | `sonic-rs` | `simd-json` |
| --- | --- | --- | --- | --- |
| typed decode, line by line | A | 2.01 ms | **1.87 ms** | 2.40 ms |
| typed decode, line by line | B | 8.45 ms | **7.40 ms** | 15.80 ms |
| typed encode, record by record | A | 2.15 ms | **0.76 ms** | 1.54 ms |
| typed encode, record by record | B | 5.05 ms | 4.99 ms | **4.64 ms** |
| untyped value, line by line | A | 2.23 ms | **1.11 ms** | not run |
| untyped value, line by line | B | 16.02 ms | **6.13 ms** | not run |

The cost of the dependency was measured too. The test is a minimal binary that
decodes and encodes one record, built with the rho release profile.

| Build | Binary size | Dependency tree | Cold build |
| --- | --- | --- | --- |
| `serde_json` only | 352 128 bytes | 21 lines | 5.0 s |
| plus `sonic-rs` | 434 784 bytes | 102 lines | 8.5 s |

```sh
cargo tree --no-dedupe | wc -l
/usr/bin/time -p cargo build --release
stat -f%z target/release/<bin>
```

The `sonic-rs` README states that a target that is neither x86_64 nor aarch64
takes a fallback path, and that the fallback can be much slower.

## Decision

`serde_json` is the default codec. `sonic-rs` is available behind a cargo feature
named `fast-json`, and the feature is off by default. `simd-json` is rejected.

`SPEC-sessions` defines the codec as one module with an `encode` and a `decode`
function. The feature switch changes the module, and it changes no caller and no
record type. The record types stay plain `serde` derives, so neither codec needs
an attribute that the other cannot read.

## Why

- **`simd-json` loses where rho lives.** It is 1.9x slower than `serde_json` on
  small records, because a per-call setup and a mutable copy cost more than the
  parse saves. A session record and an SSE chunk are both small.
- **`sonic-rs` wins the untyped path by 2.6x.** That path is the provider SSE
  reader, and it runs for every token of every turn. This is the real win.
- **`sonic-rs` wins encode by 2.9x on long text.** A session with long messages
  appends faster.
- **The default must stay small.** The feature is off by default, because
  `sonic-rs` adds 23 percent to the binary and 81 lines to the dependency tree.
  The minimal build exists to be minimal. See `ADR-footprint`.
- **Portability stays intact.** A user on an unusual target keeps the pure-Rust
  `serde_json` path, and pays no fallback penalty.
- **The append path is not codec-bound anyway.** One record is about 200 bytes,
  so an encode costs about 100 ns, while a write costs microseconds. The
  efficiency rules that matter for `store` are a buffered writer, one write per
  record, a cap on a stored tool result, and a header record that makes `list`
  cheap. `SPEC-sessions` states each rule.

## What this rules out

- No codec-specific attribute on a record type. An attribute from one crate would
  break the other crate.
- No `simd-json`, and no borrowed-value parse that ties a record's lifetime to the
  read buffer.
- No claim that rho is faster because of a JSON crate. The default build uses
  `serde_json`, the same crate as most of the ecosystem.
- No silent divergence between the two codecs. Both must produce a byte-identical
  line for the same record, and each must read the other's output. CI runs the
  codec tests twice, once with `fast-json` and once without.

## What it costs

Two code paths behind one seam. So a codec test must run in both modes, and CI
must prove both. The seam is two functions, so the cost is bounded and visible.
